# P3 环境、迁移与发布

## 1. 三套环境

| 环境 | 配置文件 | 用途 | 数据 | 访问 |
| --- | --- | --- | --- | --- |
| 开发（development） | `server/.env.example` → `server/.env` | 本地开发、单元/接口测试 | 本地 MongoDB，可随时重置 | 默认 `http://localhost:5173` → `http://127.0.0.1:5000`（本机可覆盖端口） |
| 预发布（staging） | `staging.env.example` → `.env.staging` | 生产同构演练、E2E、压力测试、验收 | 独立 MongoDB/卷，禁止生产数据 | `https://staging-crm.example.com`（示例） |
| 生产（production） | `production.env.example` → `.env.production` | 客户流量 | 独立 MongoDB/卷，备份与审计 | `https://crm.example.com`（示例） |

- `APP_ENV` 显式标记环境：`development` / `staging` / `production`。
- `NODE_ENV=production` 只表示启用生产安全/性能行为；预发布同样使用 `NODE_ENV=production`，但 `APP_ENV=staging`。
- 三套环境必须使用**不同的数据库、对象存储桶、邮件凭据、JWT/加密密钥和主机名**。
- 密钥只放在密钥管理或未入库的 env 文件；仓库只保留 `.example` 占位符。

## 2. 数据库迁移

迁移代码位于 `server/src/migrations/`，只允许前向、追加式变更：

```powershell
cd server
npm run migrate:status        # 查看已应用/待应用/校验和异常
npm run migrate -- --dry-run  # 只打印计划，不写入
npm run migrate               # 串行应用待执行迁移
npm run migrate -- --to 20261104-003-bootstrap-admin  # 仅用于本地/演练
```

规则：

1. 已应用的迁移文件禁止修改；修正必须新增更高版本迁移。
2. 每个迁移有稳定校验和 `sha256(id:version:name)`；校验和不一致时应用拒绝启动。
3. 迁移使用 `schema_migrations` 记录、`migration_locks`  advisory lock，锁 TTL 2 小时，避免多副本并发执行。
4. 应用和 worker **启动时只校验迁移是否已全部应用，不执行迁移**；有 pending/changed，或数据库存在当前镜像不认识的更新迁移记录时，均 fail closed（禁止旧镜像回滚到新 schema）。
5. 迁移必须可在生产数据量下分批执行；大表变更采用 expand/contract，先加字段/索引，再回填，最后切换代码，避免长时间锁表。
6. 生产迁移前先做 Mongo 备份，并在 staging 用等量级样本演练、记录耗时。

### Compose 中的迁移顺序

`compose.yaml` 提供一次性 `migrate` 服务，`server` 与 `worker` 通过
`depends_on: migrate: service_completed_successfully` 等待迁移成功：

```powershell
docker compose -p genesis-prod --env-file .env.production build
docker compose -p genesis-prod --env-file .env.production up -d --wait
# 仅排查问题时单独重跑迁移（不会跳过失败）：
docker compose -p genesis-prod --env-file .env.production run --rm migrate
```

`up` 会先执行 `migrate`，成功后才启动 `server`/`worker`。预发布同理，将项目名和 env 文件替换为 `genesis-staging` / `.env.staging`。不同 Compose 项目名会隔离卷和网络。

## 3. 版本与发布

- 版本号遵循 SemVer；镜像标签使用 `genesis-crm-server:<git-sha>`，禁止只用 `latest`。
- 发布顺序：构建镜像 → 在 staging 跑迁移 → 跑 `npm run test:p3` 与冒烟/负载 → 生产备份 → 生产迁移 → 滚动更新 API → 更新 worker → 健康检查 → 验证核心流程。
- 健康检查：
  - `GET /api/health/live`：进程存活；
  - `GET /api/health/ready`：数据库可用且未 draining；
  - `GET /api/health`：数据库、进程内存、邮件通道与版本。
- 回滚：
  - 应用回滚到上一镜像；
  - 数据库迁移默认**不回滚**，使用新的前向修复迁移；
  - 只有确认迁移造成破坏且已有备份时，才按备份恢复，并记录 RPO/RTO。

## 4. 发布门禁

| 门禁 | 命令/证据 |
| --- | --- |
| 类型检查 | `npm run typecheck --prefix server`、`npm run typecheck --prefix web` |
| 服务端测试 | `npm run test:p3 --prefix server` |
| 安全基线 | `npm run test:security --prefix server` |
| 依赖审计 | `npm run security:audit --prefix server`、`npm audit --omit=dev --prefix web` |
| 前端构建 | `npm run build --prefix web` |
| 服务端构建 | `npm run build --prefix server` |
| Compose 校验 | `docker compose --env-file production.env.example config --quiet` |
| 压测 | `LOAD_* npm run load --prefix server`，staging 隔离执行 |
| 法务 | 服务条款、隐私政策、DPA、SLA 经顾问复核并替换占位符 |

## 5. 预发布注意事项

- 用生产同构的 TLS、反向代理、Cookie `Secure`、CORS 和邮件配置演练，不要只测 localhost。
- 压测会触发 API 限流；只在隔离的 staging 临时提高 `API_RATE_LIMIT_MAX`，测试后恢复 600/分钟。
- 预发布禁止导入真实客户名单；使用合成数据或脱敏数据。
- 每次 schema 变更都在 staging 从头执行一次全量迁移，验证空库初始化与存量库升级两条路径。
