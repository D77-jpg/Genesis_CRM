# Genesis CRM V2.1「邮件中心」验收报告

验收日期：2026-09-10  
版本：2.1.0  
结论：V2.1 功能实现、隔离测试、原有回归、TypeScript、lint 和前后端构建均通过。真实阿里外贸邮完成无副作用连通性检查：SMTP 25 STARTTLS 认证成功，IMAP 993 SSL 认证成功并只读打开 INBOX；未发送真实邮件，也未读取邮件正文。

## 1. 实现范围

- 邮件发送从直接 SMTP 调用升级为 MongoDB 持久化任务：立即发送、定时发送、原子领取、状态历史、取消、明确临时失败指数退避重试、服务重启恢复。
- 通过请求幂等键、数据库唯一索引、原子状态迁移和固定 Message-ID 防止并发重复发送。SMTP 在 DATA 后结果不确定时进入“待核实”，不自动重发，由管理员根据邮箱服务端记录确认。
- 新增 IMAP 后台增量同步：持久化 UID/UIDVALIDITY、同步租约、单封失败隔离、失败 UID 后续重试、Message-ID/原始 MIME 哈希去重。
- 收件按规范解析主题、发件人、收件人、抄送、HTML/Text、日期、Message-ID、In-Reply-To、References 和附件。
- 发件人邮箱与 Customer.email 规范化精确匹配；唯一匹配时自动关联，零匹配或歧义时保留为未知邮件，不创建客户。
- 通过 References、In-Reply-To、Message-ID 优先建立线程，回复主题和同一客户/发件人 30 天窗口作为保守回退。回复继续走同一发送队列。
- 收件、发件和回复事件合并到原 Customer Timeline，没有新建第二套时间线。
- 新增邮件中心页面：收件箱、发件记录、定时任务、未知邮件（管理员）、详情、连续会话、附件、已读/未读、客户跳转、手动关联、回复、取消和待核实处理。
- 延续 JWT、管理员/销售角色和客户 ownerId 隔离。普通销售无法枚举未知邮件；所有无权访问继续返回 404。
- 未实现用户明确排除的追踪像素、链接追踪、AI、群发、多邮箱池、消息队列和 V2.5 功能。

## 2. 数据模型

### DevelopmentLetter（扩展）

- 新状态：queued、scheduled、sending、retrying、sent、failed、cancelled。
- 任务字段：scheduledAt、nextAttemptAt、claimedAt、attempts、needsReview、effectsPending、history。
- 幂等/会话字段：requestKey（稀疏唯一索引）、messageId、threadId、inReplyTo、references。
- 请求键按操作者做不可逆哈希；同一键内容不一致返回 409。发送成功后的 Customer 计数与状态效果通过 mailEffectIds 原子去重，支持崩溃后补偿。

### MailMessage（新增）

- 保存收件基础信息、清洗后的 HTML/Text、客户关联、线程、每用户 readBy 和安全附件元数据。
- dedupKey 是“邮箱账户标识 + Message-ID”的哈希；没有 Message-ID 时使用原始 MIME 哈希，建立唯一索引。
- 客户删除后保留最小去重墓碑，清除正文、地址、客户关系和附件，防止同一邮件再次导入。

### MailSyncState（新增）

- 按邮箱配置哈希保存 uidValidity、lastUid、failedUids、lastSyncAt、lastError、skipped。
- leaseOwner/leaseUntil 防止多个服务实例同时同步。数据库中不保存邮箱账号密码。

### Customer（扩展）

- mailEffectIds 为内部不可输出字段，用于确保并发/恢复时每封已发送邮件只更新一次 letterCount。
- 修正 email 的 MongoDB 部分唯一索引条件，非空邮箱继续唯一，未填写邮箱的客户可共存。

## 3. API

所有路径位于 /api，均先经过既有 JWT 中间件。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /mail?folder=inbox\|sent\|tasks\|unknown | 分页邮件列表；unknown 仅管理员 |
| GET | /mail/status | IMAP/SMTP 配置与同步状态，仅管理员，不返回凭据 |
| POST | /mail/sync | 触发一次后台同步，仅管理员 |
| GET | /mail/:id?direction=inbound\|outbound | 邮件详情、客户和同线程消息 |
| POST | /mail/:id/read | 标记收件已读/未读 |
| POST | /mail/:id/link | 未知邮件关联已有客户，仅管理员 |
| POST | /mail/:id/reply | 回复已关联邮件，进入统一发送队列 |
| POST | /mail/:id/cancel | 取消未开始的定时/重试任务 |
| POST | /mail/:id/resolve | 管理员确认不确定投递结果 |
| GET | /mail/:id/attachments/:attachmentId | 鉴权、按客户隔离的附件下载 |

原有 POST /letters 和 POST /letters/:id/resend 保持兼容，增加 scheduledAt、requestKey 和线程字段支持。

## 4. 发送流程

1. 服务端校验 JWT、客户归属、收件人、正文和定时时间，清洗 HTML。
2. 用 requestKey 原子 upsert DevelopmentLetter；立即任务为 queued，未来任务为 scheduled。
3. MongoDB 原子领取到期任务并转为 sending；并发 worker 只能领取一次。
4. 发送前再次检查用户状态、客户存在性和当前归属。
5. Nodemailer 使用固定 Message-ID 以及 In-Reply-To/References 发送；Mock 和真实 SMTP 共用相同路径。
6. 成功写 sent 和发送记录，并幂等更新客户计数、状态和 Timeline。
7. 仅明确“未投递”的临时错误最多重试 3 次；永久错误直接 failed。无法判定服务器是否已接受的连接中断转为 needsReview，避免自动重复投递。
8. 进程重启后扫描持久任务继续执行；超过领取租约的 sending 任务转待核实，不盲目重发。

## 5. IMAP 收件流程

1. 后台定时器启动后按数据库租约选举一次同步者。
2. 使用 IMAP UIDVALIDITY/UID 游标获取新增邮件，并穿插重试之前失败的 UID。
3. 每封邮件独立限制原始大小、解析 MIME、清洗 HTML、校验附件、计算去重键并写库；单封异常不会终止本轮。
4. 优先按 Message-ID 唯一去重，无 Message-ID 时使用稳定原始内容哈希。
5. 规范化 From 邮箱后精确查 Customer.email；只在唯一匹配时关联。
6. 依据引用头和受客户边界约束的主题回退建立 threadId，随后由既有 Timeline 动态显示收件事件。
7. 保存同步结果和错误摘要后释放租约；错误信息不包含主机响应里的密码/授权码。

阿里外贸邮最终使用 IMAP_PORT=993、IMAP_SECURE=true。实测 143 能建立 TCP，但服务器能力列表未声明 STARTTLS；系统不会降级为明文提交密码。SMTP 保留端口 25，并强制 STARTTLS。生产 TLS 证书验证没有关闭。

## 6. 内容与附件安全

- 收件 HTML 使用白名单清洗，移除 script、iframe、form、svg、事件属性、远程 img/跟踪像素、javascript URL 和 CSS URL；仅保留有限排版样式。
- 详情正文在 sandbox iframe 和严格 CSP 中呈现。
- 默认原始邮件上限 25 MiB；附件允许 TXT、PDF、PNG、JPEG，校验扩展名、MIME、文件签名和大小。可疑附件仅保留 blocked 元数据。
- 附件使用随机文件名保存到既有本地上传目录，不公开静态路径，下载必须再次鉴权。
- SMTP_PASS、IMAP_PASSWORD、JWT_SECRET 只从环境变量读取，不写数据库、不记录到日志；seed 日志也不再输出管理员密码。

## 7. 权限验收

- 销售只可查看、标记、回复和下载自己客户关联的邮件。
- 销售访问其他客户的收件、发件、线程、附件、取消、回复及旧 /letters?customerId 查询均返回 404。
- 未关联邮件、同步状态、手动关联和投递结果核实仅管理员可访问；普通销售得到 404。
- 管理员可以跨销售访问，但线程查询仍按当前邮件的 customerId 收敛，伪造相同 threadId 不能混入其他客户。
- 已读状态按用户单独保存，销售和管理员互不影响。

## 10. 已知限制与上线前动作

1. 真实邮箱当前已通过 SMTP 25 STARTTLS 与 IMAP 993 SSL 认证检查。验证脚本只执行 SMTP verify 和 IMAP 只读锁定，不发送、不下载、不输出凭据。实际投递仍应由用户指定收件人后另行验证。
2. 系统当前是单邮箱配置，符合本期范围；多邮箱账号池不在 V2.1。
3. 分布式语义采用 MongoDB 原子任务。SMTP 协议无法在客户端与远端服务器之间提供严格事务；不确定结果通过人工核实避免自动重复发送。
4. Node.js 最低版本为 20.19.0，这是当前 ImapFlow/MailParser 依赖要求。
5. 最新 npm audit：后端仅剩既有 xlsx 1 个 high（npm 无可用修复）；前端剩 4 个 moderate、1 个 high，来自既有 react-quill/quill、react-router-dom 6 和 xlsx。修复需要编辑器/路由大版本迁移或替换 Excel 库，未在邮件中心版本中冒险变更。V2.1 收件正文仍经过服务端清洗并在 sandbox iframe 中呈现。
6. ESLint 的 6 条 warning 均为原有 Fast Refresh 文件导出提示和 templates.tsx 的 useMemo 依赖提示，没有 lint error。
7. 本机已安装 MongoDB Community Server 8.3.7，Windows 服务设置为自动启动；当前 MONGODB_URI 连接成功。管理员账号已初始化，指定密码的登录验证通过。
