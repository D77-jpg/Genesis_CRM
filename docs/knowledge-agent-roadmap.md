# Genesis CRM：项目知识库与销售 Agent 后续开发规划

日期：2026-10-17（北京时间）

本规划是后续开发与验收的执行合同，不代表下列能力已经实现。目标是在现有 CRM 内自主开发；参考开源项目的思路与代码组织，不接入 RAGFlow、Dify 等整套知识库/Agent 平台代替自己的系统。

## 1. 当前基线与最终范围

规划核对基线：Genesis_CRM main `1c78bbe`，包含知识库 PR #30。

正式开发目录：`D:\Trade\genesis\CRM\Genesis_CRM`。开工时重新确认目录、AGENTS.md、最新 main 和工作区，不把本文件中的 SHA 当作以后固定起点。

现有技术栈：React/TypeScript、Express/TypeScript、MongoDB；已有客户、邮件线程、模板、个人邮箱权限、后台 Agent 任务、知识版本及人工审核草稿。当前知识检索是关键词/别名匹配，无向量化、重排序及正式检索质量基准。

现有自动化测试是安全和流程基线，不能替代检索质量评测。Genesis Bags 资料包已整理的 82 条知识仍为草稿，不能因执行本规划而自动发布；此前输出的“通过”也不能视为企业级能力已验收。

最终必须覆盖：

- 多项目、多业务员的权限隔离；Genesis Bags 与 IRONHUE 不串用知识、条件或签名。
- 公司、产品、政策、合规、销售规则、FAQ 的录入、来源、版本、审核、生效、停用和替代关系。
- TXT、Markdown、文本型 PDF、DOCX、XLSX、CSV 的知识导入，以及扫描 PDF/PNG/JPEG 的本地 OCR 处理；失败必须显式，不得假装已读懂。
- 文档结构、标题、表格表头、单位、脚注与原文位置保留；形成可审核、可检索的知识片段。
- 自己管理的向量化、关键词与语义混合检索、融合、重排序、版本同步和异常降级。
- 基于当前项目、客户、授权邮件线程、有效专属约定生成开发信、询盘回复、报价说明、样品回复和跟进信。
- 对关键业务事实、条件、未知信息和冲突做核对；内部证据不混入客户正文。
- 草稿人工审核、修改后再核对、旧依据变化提示与显式重新生成；Agent 始终不自动发送真实邮件。
- 可重复评测、运行记录、故障诊断、备份恢复、升级/回滚说明和完整本地业务验收。

本轮范围不包括：数字人/直播、全网自动爬取、全面 ERP/库存系统、自动认证真伪鉴定、自动发信、生产部署，以及为追求名词而引入知识图谱。PPT/PPTX、音视频和 CAD 等格式属于后续扩展，不能显示为已支持。

## 2. 自主系统的架构边界

```text
原始资料 → 安全校验 → 解析/OCR → 结构化分块 → 人工审核发布
                                         ↓
                           条件事实库 + 文档片段索引
                                         ↓
当前项目/客户/线程 → 问题拆解 → 权限与版本过滤
                             ↙             ↘
                         关键词召回       向量召回
                             ↘             ↙
                             融合 → 重排序 → 证据包
                                         ↓
                 条件/时效/冲突核对 → 草稿生成 → 事实核对
                                         ↓
                         人工审核 → 业务员发送 → 实际跟进
```

- MongoDB 中的业务记录是知识发布、版本和权限的权威来源。向量索引是可重建的派生数据。
- 可使用经过选型的通用解析库、OCR/Embedding/Rerank 模型和向量索引组件；不必重新发明模型或索引算法。业务 API、界面、数据模型、任务状态、权限、检索策略、Agent 工作流及评测归我们自己的系统控制。
- 底层需要单独的本地进程时，可作为内部组件/工作进程存在，不另起一套让业务员使用的知识管理平台。
- 向量“相似”只说明可能相关，不证明适用。项目、客户、数量、产品、工艺、币种、计价单位和有效期需要独立核对。
- 检索服务返回内容前必须落实权限过滤；组装证据包前再次核对权威版本。不能先把其他项目原文交给模型，再试图依靠提示词或最后过滤补救。
- 草稿、模板、客户来信和客户网页都不自动成为我方政策。客户约定只在其明确定义的范围内适用。
- 默认本地解析/OCR/向量化。已有聊天模型配置不等于已有 Embedding/Rerank 服务；真实文件向外部模型或服务传输必须符合用户对具体资料和目的地的授权。独立虚构测试数据可按已有授权使用。

## 4. 最终验收门槛

以下是建议初始门槛，S0 应固定数据集、计算方法和测试机器配置。若必须调整，列明原因和影响，由用户确认；不能在结果不理想后偷偷放宽门槛。

| 项目 | 门槛 |
| --- | --- |
| 项目/用户/个人邮箱隔离 | 授权测试与攻击测试中，越权内容进入检索结果、缓存或模型上下文的次数为 0 |
| 过期/停用/未发布知识 | 不作为当前业务依据；0 次误用 |
| 禁止编造的承诺 | 评测中未获依据的价格、MOQ、交期、运费、认证等对外承诺为 0；不把此有限测试结果宣称为永远零幻觉 |
| 关键承诺追溯 | 每项有 source/version/原文位置及适用条件，正确覆盖率 100% |
| 检索召回 | 在固定、有答案的保留评测集上，多依据 Recall@10 平均值至少 90%；单列中文、英文和跨语言结果 |
| 强约束案例 | 指定关键政策及客户专属约定案例全部找到适用依据或明确阻断，不以泛化召回平均值掩盖失败 |
| 客户问题覆盖 | 有充分有效依据的问题，正确回答覆盖率至少 90%；无答案、冲突和故障另行统计，不充作正确回答 |
| 引用正确性 | 普通事实引用支持率至少 95%；关键承诺仍要求 100%，错误来源不能只因 ID 存在而算正确 |
| 无答案处理 | 缺资料/过期/冲突/故障状态识别准确率至少 95%；故障、越权或证据不足时不得形成无依据承诺 |
| 生命周期 | 发布、更新、停用、重建、模型版本迁移后无旧政策误用；旧草稿不被静默改写 |
| 业务完整性 | 五类邮件任务及草稿审核闭环通过；重试不重复创建草稿/跟进；自动发送真实邮件次数为 0 |
| 性能 | 建议初始目标：固定机器、1 万片段、并发 2、模型已加载，检索含查询向量化和重排的 P95 ≤ 5 秒；冷启动、解析和整封邮件生成分别报告 |
| 故障恢复 | 解析/索引/检索/模型超时、中途重启、索引丢失可恢复或明确安全失败；无静默假成功 |

评测集至少 120 题，建议 80 题有依据、40 题无依据/冲突/过期/攻击等，开发集和保留集各 60 题、各类均衡。保留集不用于反复调参数；如果调参使用过，就不能继续当未见测试集，应补充新的独立保留样本。

标注至少记录：问题语言、项目/角色/客户范围、预期条目/片段/版本/位置、适用条件、应答事实、禁止承诺、预期拒答或缺口状态。Recall@10 针对有答案样本，按每题找到的必要依据数/应找到依据数计算后平均，不与无答案样本混算。MRR、排名质量、人工邮件评分、检索成本和延迟也记录，但不以单一总分掩盖安全失败。

有限 fixture 通过不等于生产零风险。最终还必须由业务负责人审核真实资料的真实性、条件边界及邮件可用性。

### S1：文档入库、OCR、结构化分块与来源定位

交付重点：资料从原文到可审核片段的完整路径。大型阶段可拆为 S1a 文本/Office/PDF、S1b OCR、S1c 发布与片段预览，每步单独合入。

```text
请执行 Genesis CRM 自研知识库 S1。先读取 D:\Trade\genesis\CRM\Genesis_CRM 的规范、最新 main、S0 架构合同/评测报告和阶段进度，验证前置阶段已经合入。沿用现有 CRM，不接入独立知识库平台。

实现原始文档→安全校验→持久解析任务→结构化片段→预览审核的完整流程：
- 支持 UTF-8 TXT/Markdown、文本型 PDF、DOCX、XLSX、CSV；扫描 PDF、PNG/JPEG 走选定的本地 OCR，不能把空正文当成功。
- 依据格式、大小、页数、工作表和解压后规模设限，不执行宏、脚本、文档指令和外部链接；解析进程有超时与资源限制。
- 保留文件哈希、解析器版本、标题路径、页码/工作表/单元格或文本区间、表格表头、币种单位及脚注关联。分块不能切断 MOQ/价格/工艺和条件；超长表格分段需重复表头。
- 去重、逐文件失败、重试、取消、重启恢复必须真实可用；错误和无法识别的内容明确标注。
- 自动抽取只形成待审核建议，不自动生成已发布政策。保留现有知识版本及 82 条草稿，建立兼容映射和迁移预览，不删除或覆盖。
- 提供上传、解析进度、片段/原文定位、失败原因和审核入口；不显示未实现格式。界面遵循现有 CRM，适合业务员使用。

用独立样本验证中英文、表格脚注、扫描件、低质量 OCR、重复文件和恶意文件；真实资料默认本地处理，不向外部服务传输未经授权资料。运行必要回归，不发真实邮件、不修改真实客户。按最新 main 的短命分支分步提交推送，由我按规范创建/合并 PR；更新阶段进度、操作说明、测试和截图，明确不支持的情况。
```

### S2：向量化、持久索引与知识生命周期

交付重点：真实语义向量，发布后可检索、停用后立即不可用，失败可恢复。Embedding 版本变化需要重建流程，不能混用维度或模型。

```text

使用 S0 选定的真实本地 Embedding 和索引组件，为已审核发布片段建立语义索引。实现我们自己的 Embedding 适配接口、持久索引任务、幂等键、批次、重试、断点恢复和管理状态。

记录 projectId、知识/文档/片段 ID、发布版本、内容哈希、模型标识及版本、维度和索引代次。相同内容只在权限允许的项目范围内复用；查询与文档向量必须属于兼容模型版本。禁止随机、散列或关键词向量冒充语义模型。

MongoDB 是发布与权限的权威，索引可重建。发布、更新、停用、失效、删除和访问范围变化必须同步。索引未就绪或落后时明确状态，不能悄悄回用旧政策。新索引代次完整验证后再切换；失败可回滚，支持重建和旧代次清理。候选返回前做权限过滤，证据包组装前再次核对有效版本；缓存键也包含项目、权限和索引版本。

独立验证实际向量生成、跨语言相似检索、停用立即生效、中断恢复、重复任务、维度变更、迁移和重建，不外传未经授权真实资料、不发真实邮件。提供管理员可用的索引状态/重试入口。遵守独立分支、测试后 commit/push、由我创建/合并 PR 的规范；更新进度和运行记录，报告本地真实模型与 mock 的区别。
```

### S3：混合召回、融合、重排序与检索质量

交付重点：从“有向量”升级为“找得到正确依据”。在开发集调参，在独立保留集测量，不能给固定问题硬编码答案。

