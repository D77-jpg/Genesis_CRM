# Genesis CRM V2.6「多项目工作空间」验收报告

验收日期：2026-09-10  
版本：2.6.0  
结论：通过。现有 Genesis Bags CRM 已升级为一套部署、多项目工作空间架构，内置 Genesis Bags 与 IRONHUE，并支持管理员继续创建其他外贸项目。V1、V2、V2.1 邮件中心与 V2.5 邮件行为追踪保持可用。

## 1. 交付范围

- 一个账号可按权限进入一个或多个项目，顶部随时切换当前工作空间。
- 客户、开发信/发送任务、收件邮件、邮件线程、Open/Click Tracking、跟进、Timeline、附件、模板、报价和 Dashboard 统计全部按项目隔离。
- 管理员可创建、编辑、归档/恢复项目；默认 Genesis Bags 不允许归档。
- 管理员可在用户管理中勾选业务员可访问的项目；业务员仍只能查看自己负责的客户。
- Genesis Bags 继续使用原有 SMTP/IMAP 配置；IRONHUE 和未来项目可使用独立服务端邮箱配置。
- 未开发跨项目群发、AI 自动化、WhatsApp/LinkedIn 自动化或 V3 功能。

## 3. 数据模型与索引

### Project

项目主档保存：`name`、`slug`、`code`、`industry`、`companyName`、`website`、`moq`、`senderName`、`mailFrom`、`mailProfileKey`、`status`、`isDefault`。`slug` 与 `code` 全局唯一；邮箱密码、授权码不入库。

### 业务归属

以下集合均有必填 `projectId`：Customer、DevelopmentLetter/Email Job、FollowUp、CustomerEvent、CustomerAttachment、Quotation、LetterTemplate、MailMessage、MailSyncState。

关键唯一约束由“全局唯一”改为“项目内唯一”：

- 客户邮箱：`{ projectId, email }`。
- 报价编号：`{ projectId, quotationNo }`。
- 邮件任务幂等键：`{ projectId, requestKey }`，且只对字符串字段建立 partial unique index。
- 收件去重键：`{ projectId, dedupKey }`。

因此同一个客户邮箱、报价编号或发送请求键可合法存在于 Genesis Bags 与 IRONHUE，但同一项目内仍会拒绝重复。

### 用户授权

- `projectIds`：普通用户可进入的项目集合。
- `defaultProjectId`：旧客户端未传项目头时的兼容回退。
- 系统管理员是跨项目管理员，可进入所有启用项目；普通业务员必须同时满足“项目成员”和“客户负责人”两层权限。

## 4. Project API 与业务请求

### 项目管理

- `GET /api/projects`：登录后可用；管理员返回全部项目，普通用户只返回获授权的启用项目。
- `POST /api/projects`：仅管理员；创建独立工作空间。
- `PUT /api/projects/:id`：仅管理员；编辑品牌/邮箱配置键，或归档/恢复项目。

默认项目不能归档；归档只停止访问，不删除任何业务数据。

### 当前工作空间

前端在业务请求中发送 `X-Project-Id: <随机 Mongo ObjectId>`。后端会校验项目存在、处于启用状态且当前用户有权进入，然后把项目范围加入每个业务查询。伪造、未知、已归档或无成员权限的项目头返回 404，不披露项目或业务数据是否存在。

为兼容 V1–V2.5 客户端，未发送请求头时回退到用户默认项目；新前端始终显式发送当前项目。

## 5. 历史数据迁移

启动时执行幂等迁移：

1. 创建/确认默认项目 Genesis Bags。
2. 创建/确认空的 IRONHUE 项目。
3. 所有缺少 `projectId` 的 V1–V2.5 业务数据归入 Genesis Bags。
4. 所有尚无项目授权的历史用户加入 Genesis Bags，并设为默认项目。
5. 删除四个旧全局唯一索引，再由 Mongoose 创建项目复合唯一索引。

重复启动不会复制项目或迁移出第二份数据。生产升级前仍建议备份 MongoDB 与上传目录。

## 6. 邮件、线程与 Tracking 隔离

- 发件任务创建时固化 `projectId`、收件人、发件显示地址和公司占位符结果；队列重试不会切换到其他项目配置。
- 邮件队列在投递前再次验证客户、发件用户和项目成员关系。
- IMAP 按项目独立配置、同步锁、UID 游标、去重键与附件目录运行。
- 相同 Message-ID 在两个项目邮箱中可各自导入，不会错误合并线程或匹配另一项目客户。
- Open/Click Tracking 的公开随机 token 机制保持不变；内部查看互动数据时增加项目范围，无法跨项目读详情。
- 删除客户时只取消/清理当前项目邮件，附件优先清理 `uploads/mail/<projectId>/`，并兼容 V2.1/V2.5 旧路径。

## 7. SMTP/IMAP 配置隔离

Genesis Bags 继续读取既有 `MAIL_TRANSPORT`、`MAIL_FROM`、`SMTP_*` 与 `IMAP_*`，不要求重新配置。其他项目使用：

```env
PROJECT_MAIL_CONFIGS_JSON={"ironhue":{"transport":"smtp","mailFrom":"IRONHUE <sales@example.com>","smtp":{"host":"smtp.example.com","port":587,"secure":false,"requireTLS":true,"user":"sales@example.com","pass":"authorization-code"},"imap":{"enabled":true,"host":"imap.example.com","port":993,"secure":true,"user":"sales@example.com","password":"authorization-code","mailbox":"INBOX"}}}
```

键名与项目 `mailProfileKey` 对应。未配置的非默认项目使用 Mock 且禁用 IMAP，因此不会误用 Genesis 邮箱。配置只存在于服务端环境变量，浏览器和项目 API 均不返回凭据。

## 11. 已知限制与部署注意事项

1. 系统管理员按设计可查看全部项目；当前版本没有“仅管理某一个项目的项目管理员”角色。
2. 项目归档保留全部数据且不可进入；未提供永久删除项目，避免误删整个业务空间。
3. 现有记录不支持在项目之间直接移动。需要纠正归属时应通过当前项目导出、目标项目导入，并在确认后清理原记录。
4. SMTP/IMAP 密钥仍由运维人员放入服务端环境变量，修改后需重启后端；管理页面只维护非敏感品牌资料和 `mailProfileKey`。
5. 第一次生产升级会迁移历史记录并重建相关索引，建议先备份并在低峰期重启一次。
6. lint 的 6 条 warning 为既有 Fast Refresh 导出规则与模板页 Hook dependency 提示；没有 error，不影响构建和运行。
7. 当前局域网入口依赖本机 DHCP 地址 `192.168.1.16`；地址变化后应使用新的局域网 IPv4，或在路由器中为本机保留固定地址。仅建议在可信局域网使用，不要配置公网端口转发。
8. Windows 当前已有启用的 Node.js 公用网络入站放行规则，范围比本应用端口更宽；本次未擅自修改系统级既有规则。如需最小权限部署，应以管理员身份将规则收紧到 TCP 5173/5000 和可信子网。

启动兼容热修复：开发命令已兼容部分 Windows + Node 24 环境的 `os.userInfo()` ENOMEM；SMTP 连通自检改为后台执行，网络不可用时不再阻塞 CRM 登录。旧 sparse requestKey 索引会在启动迁移中安全替换为最终条件索引。

V2.6 到此停止，未开始 V3。
