# 客户草稿审核入口

## 问题与行为

客户转化后准备的开发信已保存为 DevelopmentLetter 草稿，但销售助手只列最近的 AgentTask，缺少关联任务的旧稿、手动稿或其它人准备的可访问草稿不会出现。客户历史与全局开发信记录把草稿的“重新发送”按钮禁用，也没有替代的审核编辑入口。

现在客户详情顶部展示当前客户所有可访问的未发送草稿；销售助手对话里提示待审数量，待办顶部展示已保存草稿。数据按 status=draft 分页查询现有开发信接口，独立于任务最近 30 条的限制。任务区域单独标为“助手任务进度”，不再把没有任务误述为没有草稿。

客户历史、开发信记录（桌面和紧凑布局）与查看弹窗均提供“审核草稿”。统一通过客户页 knowledgeDraft 链接取完整详情，核对客户和 draft 状态，再打开原有审核编辑器。审核器支持修改、继续存草稿、展开内部依据以及人工确认发送。保存或删除后刷新待审列表，打开期间每 10 秒同步，重新聚焦窗口时同步；切换客户/账号/项目后不展示旧范围结果，失败可重试。每页 5 封，支持翻页和页数缩减。

## 权限与验证

复用已有客户、项目和负责人权限接口，未新增权限或自动发送。草稿计数以已保存邮件为准，不以任务存在为前提。

本地前端生产构建、工作流 5 项与客户/起草 5 项回归通过。独立内存数据库的浏览器验证使用无关联 AgentTask 的虚构旧稿：客户详情可见 → 助手提示 1 封 → 待办可打开审核 → 修改主题 → 存草稿 → 再次打开仍保留修改。草稿总数保持 1，状态未发送、客户尚未联系；内部审核依据可展开；从全局开发信记录点击“审核草稿”也可打开同一编辑器。未使用真实客户、真实模型或真实邮件投递验证。

## 审核结论与界面改版（2026-10-22）

### 原问题

审核弹窗把“客户/发件人、收件人、主题、正文、模板、定时发送、联系状态、依据与风险、内部审核信息”全部纵向堆在一列，依据面板默认展开，长内容把正文和结论都推到视线之外；底部只有“存草稿 / 发送”，没有表达“通过 / 不通过”的决策，业务员只能靠“不点发送”来表达“这封不能用”，草稿上也不留任何结论。

### 现在的界面

- 弹窗加宽为两列（≥lg）：左列“要发给客户的内容”，右列“依据 + 结论 + 发送设置”，右列 sticky。
- 左列：客户与发件人摘要卡（收件人、发件邮箱、通道、能否发送、状态）→ 邮件内容卡（模板导入、收件人、主题、编辑/预览/中英对照）→ 校验提示。
- 右列：**审核结论**卡（当前状态徽标、结论说明、三步核对清单）→ **依据与风险**（收起态，标题右侧显示是否需要确认）→ **发送设置**（定时发送、发送后标记已联系、通道）。
- 底部：`取消 / 存草稿 / 不通过（或撤销标记）/ 主按钮`。主按钮随状态变化：待审核、已标记不通过或内容被改动 → `审核通过`（发件邮箱未就绪）或 `审核通过并发送`；已通过未修改 → `发送开发信`。
- `不通过` 一键生效，不需要理由：弹窗关闭、草稿从“待处理”清单移出，提示条给出「撤销标记」。

### 二次修订：审核是业务员自检（同日）

第一版按“审核人 → 撰写人”的转交流程设计：退回必须写原因、列表显示审核人与退回原因。实际情况是这份草稿就是业务员自己生成、自己决定发不发，退回原因没有接收方，填理由纯属负担。因此：

- 结论只剩两个动作：**通过**（可以发）与 **不通过**（这封不用了），都是对自己负责，不写理由、不做转交。
- 数据里彻底去掉 `note` 字段；`byName` 仍保留（审计用），但界面不再显示“审核人”，因为就是本人。
- “不通过”的草稿默认不占清单：列表拆成 `待处理 / 不通过` 两个视图（服务端 `review=todo|rejected` 过滤，分页与计数都按筛选后的结果算），想翻旧稿切到 `不通过` 视图，按钮变成 `重新审核`。
- 结论可反复改写：`不通过` 后点主按钮即变 `通过`；也可 `撤销标记`（`decision:'clear'`）回到待审核。
- 保存草稿（改内容）一律清除旧结论，回到待审核；不再出现“改完了还挂着已通过/已退回”的状态残留。

### 状态判定

`DevelopmentLetter.review` 保存 `{decision, at, by, byName, contentHash}`，`contentHash = sha256(JSON.stringify([subject, contentText]))`。列表与弹窗按同一口径判定：

| 情况 | 显示 |
| --- | --- |
| 无 review | 待审核 |
| `approved` 且 hash 与当前内容一致 | 审核已通过 |
| `approved` 但本地改过主题/正文 | 需重新审核 |
| `rejected` | 不通过（列表）/ 已标记不通过（弹窗） |

- 保存草稿（`saveAsDraft`）一律 `$unset` 旧的 review：改了内容就重新给结论，不保留任何一侧的结论。
- 发送前再次校验：`rejected` 返回 409「草稿已标记为不通过，请先审核通过再发送」；被改动过的 `approved` 返回 409「审核后内容已变化，请重新审核后再发送」，防止绕过 UI 直接发送。

### 接口

`POST /api/letters/:id/review`

- 请求：`{ decision: 'approve' | 'reject' | 'clear', subject?, content?, recipientEmail? }`，三个动作都不接受理由字段。
- `approve` 会把本次编辑后的主题/正文/收件人一并落库，再写入 review 与新的 contentHash；`reject` 只写结论，不保存未提交的修改（有问题的稿子也能直接判掉）；`clear` 只 `$unset` review，草稿回到待审核。
- 返回：更新后的 `LetterDto`（`clear` 之后不含 `review`）。
- 冲突：非草稿 409；草稿状态已被并发改动 409。审核结论不触发发送，发送仍走既有 `/letters/:id/resend`（send 前同样校验 review）。
- 列表接口 `GET /api/letters` 新增 `review=all|todo|pending|approved|rejected`：`todo` 用 `{'review.decision': {$ne: 'rejected'}}` 匹配（缺字段的旧稿也会命中），筛选走 `$and`，不会和 `search` 的 `$or` 互相覆盖。

### 兼容与边界

- 老的草稿没有 `review` 字段，一律按“待审核”处理，不阻塞既有自动化链路；保存草稿时写入的 `review: {}` 由 `activeReview()`（要求 `decision` 与 `contentHash` 同时存在）过滤。
- 发送草稿仍会新建一条 sent 记录并保留原草稿行（agent 依赖 `agentDraftId`/`requestKey`），因此已通过的草稿继续留在“待处理”视图（徽标 `审核已通过`、按钮 `查看草稿`），只有明确标记不通过的才移出清单。
- 不通过不改变客户状态、不发送邮件；`onReviewed` 只刷新客户页的草稿列表。

### 验证

- 服务端 `test:mail` 97 项通过，新增用例覆盖：无理由 `reject` 返回 200、不通过后发送 409、保存草稿后结论清空、`approve` 后 hash 长度 64 与操作人、通过后改内容发送 409、通过后发送新建记录、无 review 的老稿可发送、`reject → approve` 可翻转、`clear` 后恢复可发送、`review=todo|pending|rejected` 三种筛选结果正确。
- 浏览器验证（本地真实数据）：`不通过` 一键生效并关闭弹窗 → 待处理视图不再出现该草稿、`review=todo` 接口也查不到；切到 `不通过` 视图可见该草稿，徽标 `不通过`、按钮 `重新审核`；`撤销标记` 后接口 `review` 为空、草稿回到待处理；1440 宽两列布局无横向溢出。
