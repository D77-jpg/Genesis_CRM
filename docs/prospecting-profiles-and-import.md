# 今日开发：搜索方案与客户资料交接

## 原因与调整

旧链路把搜索结果标题同时存成公司名；官网补全找到邮箱就退出，实际很少读到联系页和关于页。国家虽有字段但写入候选时遗漏；Hunter 的组织名被丢弃，职位仅塞入备注，Instagram/LinkedIn 未传到客户字段。

现在官网补全最多仍读取 3 个页面，优先首页及其真实联系/关于链接，不因邮箱出现提前停止。保留页脚，读取原始 HTML 中同域 Organization 的 JSON-LD，提取明确的公司、电话、国家、地址、行业和社交链接；同时支持明确的联系方式标签。不从商品品类、销售区域或搜索词推断采购需求和国籍。

Hunter 仍仅在官网没有邮箱且本轮预算允许时调用。保留组织名、首选邮箱对应的姓名/职位/电话/LinkedIn；不会把另一个邮箱的人名套给首选邮箱。没有额外调用公司付费 enrichment 接口，也不假设 Domain Search 必然返回地址、国家或行业。

转客户保留所有已获取字段，搜索与官网简介、其它公开邮箱和来源进备注。转换前可展开“查看将导入客户的资料”。旧客户可点“补齐已获取资料”：按当前项目和客户权限，只填空字段，保留人工编辑，重复操作不重复追加备注。它使用已保存的候选，不额外调用第三方 API；历史上未采到或已丢失的资料，可由管理员点“重新采集并补齐空字段”重新读取最多 3 个官网页面，并补齐当前客户空字段；会消耗 Firecrawl 额度，不调用 Hunter 或模型。服务端每候选互斥且成功后 1 分钟内不重复采集；无可读资料时明确失败，不改客户。备注有 5000 字上限，已有长备注不会被覆盖。

## 搜索方案

每个项目最多 20 套命名方案，独立保存关键词（最多 20 条）、补全数量、Hunter 上限、入选分数与画像评分开关。可新增、复制、改名、移除；至少保留一套。原单套配置无损呈现为“原默认方案”，零预算、零分和评分关闭均保留。

每天自动生成沿用项目时间/开关并采用指定默认方案；手动生成可另选方案和临时修改关键词/数量。运行保存方案名称、关键词和预算快照，启动后修改或删除方案不改变本轮，也不修改自动任务默认配置。保存带版本号，拒绝覆盖别人刚保存的设置。API 与修改权限仍只对管理员开放。

## 正文模式切换

模板、收件邮箱和主题为共享字段；编辑/预览/中英对照栏移动到正文上方，并在滚动时保持可用。切换保留主题、收件人和正文，翻译仍只作对照，不覆盖英文。

## 验证

- 今日开发专项 20 项通过；包含模拟第三方响应 → 原始官网结构化字段 → 候选入库 → 客户创建的真实内存数据库集成测试。
- Agent、官网研究和今日开发合计 109 项相关回归通过。严格类型检查与前后端构建通过；专项测试已接入 CI，但尚未把本地结果视为远端 CI 结果。
- 浏览器在独立虚构数据库中完成：旧单方案 → 改名并复制第二方案 → 保存 → 手动生成切换方案，关键词/数量正确回填；候选预览 → 转客户 → 客户档案确认职位、公司、电话、国家、行业、社交字段。
- 修改主题后切换预览、中英对照、返回编辑，英文和主题保留；正文切换栏紧邻正文。测试环境禁止外部 API，模拟翻译返回解析失败时显示重试提示，未评测真实翻译质量，也未发送真实邮件。

可复用的 UI 夹具：在 server 下执行 node --require ./tests/os-user-info.cjs --import tsx tests/prospecting-ui-fixture.ts；PROSPECT_UI_PORT 指定端口。只创建内存数据库，禁止真实外部请求，无邮件与 Agent worker。

接口契约参考：[Hunter Domain Search](https://hunter.io/api-documentation/v2#domain-search)、[Firecrawl v1 scrape](https://docs.firecrawl.dev/api-reference/v1-endpoint/scrape)。
