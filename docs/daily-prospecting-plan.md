# 每日自动开发客户：方案（2026-10-21）

目标：每个项目每天自动产出 15 个“可以发信”的新客户草稿；业务员在固定时间只做审核与发送。

已定（2026-10-21）：

- 线索来源：**第三方线索 API**（不做平台采集）；
- 入库方式：**候选池 → 业务员审核 → 转正式客户**；
- 时间与归属先用默认值：06:30 生成、09:30 审核发送、客户归属该项目绑定的业务员，后续可配。

## 一、现有能力与缺口

可以直接复用：

- 客户档案（姓名/公司/邮箱/官网/国家/等级/状态）与 Excel 导入；
- 官网研究 `WebsiteResearch`（抓官网并留存快照）；
- 知识库 RAG + 证据审计（价格/MOQ/交期不会被编造）；
- 首封开发信任务链：定位客户 → 研究官网 → 分析起草 → 保存草稿 → 核对；
- `AgentBatch`：同一个目标批量跑多个客户，带总 token 预算；
- Agent 配额、审计、人工发送（发送永远需要人点）。

目前缺的：

1. **没有“找新客户”的来源**。系统只会研究和写信给“已经存在的客户”，不会凭空产生线索。
2. 没有每日调度器，也没有“线索/候选池”的数据模型（去重、冷却、评分、批次）。
3. 没有“今日开发”批量审核页面。
4. `CUSTOMER_SOURCE` 只有 manual/excel/seed/integration，没有 `prospecting`。
5. 自动建客户会污染 CRM，需要候选池 + 审核后再转客户。

## 二、线索来源：Serper + Firecrawl（已接入）

两个供应商分工明确：

- **Serper**（`google.serper.dev/search`）= 发现。用画像里的搜索词跑 Google，拿品牌官网域名；按域名去重，过滤 Etsy/Amazon/Pinterest 等平台站。
- **Firecrawl**（`api.firecrawl.dev/v1/scrape`）= 补全。抓官网首页 + `/contact` + `/about` 的 markdown，提取邮箱、Instagram、LinkedIn、公司名。

两把 key 已写入 `server/.env`（`LEAD_SERPER_API_KEY` / `LEAD_FIRECRAWL_API_KEY`，`.env` 已在 `.gitignore`），不落库、不回传前端。代码在 `server/src/services/prospecting/lead-source.ts`，可以用 `npx tsx src/scripts/prospect-dry-run.ts` 试跑，不写数据库。

**实跑结果（2026-10-21，3 个查询 × 8 条）**：

- 去重后 21 个域名；补全前 4 个，只有 2 个在页面上找到邮箱；
- 结果里混着目录站（MakersRow）、零售商（candlestore.com）、供应商（lonestarcandlesupply.com）、协会（gemsociety.org）；
- 不少品牌官网只有联系表单或 Instagram，没有公开邮箱。

因此这条链的真实约束是：**搜索只能给“候选域名”，邮箱要靠抓取，且不是每个都有**。方案上要接受：

1. 每天拉 60–100 个候选域名，补全 30–50 个，评分后取 15；
2. 没有邮箱的候选标记“需人工找联系方式”，不硬凑；
3. 评分阶段必须能识别并排除目录站/零售商/供应商/协会（用画像 + 页面内容判断）；
4. Firecrawl 按页计费，补全要限量（首页 + 最多 2 个联系页）。


实现约定：

- **凭据放服务端 `.env`**（如 `LEAD_API_KEY_APOLLO`），不落库、不回传前端；项目级配置只选 provider 与筛选条件。
- 每日拉取量：目标 15，实际拉 40–60 条进候选池，评分后取前 15；记录每次 API 消耗。
- 限流与失败：429/5xx 指数退避，最多 3 次；失败写入 `ProspectingRun.error`，当天不重试超过预算。
- 去重：domain 优先、email 其次；与 CRM、候选池、90 天发送记录三方比对。
- 合规：只使用供应商授权数据；保存 `sourceUrl` 与获取时间；提供按项目删除候选的能力。

下一步：把 dry run 接进 `Prospect` 候选池，加上评分与“今日开发”页面。

## 三、每日流程

```
06:30  Serper 搜索（画像关键词 × 目标国家）→ 域名去重
       → 冷却检查（90 天内不重复触达）
       → Firecrawl 补全（首页 + 联系页，提取邮箱/IG/LinkedIn）
       → 画像评分（01-客户画像，LLM 结构化打分 + 理由）
       → 硬性排除（目录站/零售商/供应商/无联系方式/国家不符/黑名单）
       → 取前 15 个（不足则记录缺口，不凑数）
       → 写入候选池 → 生成首封草稿（知识库依据 + 证据审计）
09:30  业务员打开“今日开发”，逐条审核、改、发送（或跳过）
18:00  回收状态：已发 / 回复 / 退信；未处理的草稿次日提醒，3 天过期
```

## 四、数据模型（新增）

- `Prospect`（候选池，项目隔离）
  - `projectId, domain, name, company, website, country, contactName, email, source, sourceUrl`
  - `score, scoreReasons[], status: new|scored|drafted|approved|rejected|converted`
  - `dedupeHash`（domain 优先）、`customerId`、`day`、`createdAt`
  - 唯一索引：`projectId + domain`（或 `projectId + email`）
- `ProspectingRun`（每日运行）
  - `projectId, day, status: running|completed|partial|failed`
  - `imported, deduped, excluded, scored, selected, drafted, failed[]`
  - `startedAt, endedAt, error`
- `ProjectProspectingConfig`
  - `enabled, dailyTarget=15, runAt, reviewAt, timezone, ownerId, minScore=60, cooldownDays=90, sources[]`
- `Customer` 增加 `source='prospecting'` 与 `prospectId`

## 五、服务与调度

- 新增 `prospecting.service`，按阶段拆分，可单步重试：`import → dedupe → enrich → score → select → create → draft → qa`。
- 调度器：每分钟检查 `ProjectProspectingConfig.runAt`（按项目时区），用 `day + projectId` 做幂等键，进程重启不会重复跑。
- 批量写草稿复用 `AgentBatch`（每批 15 个客户，总预算上限）；单条失败重试 ≤2，不影响其他客户。
- 每日配额：15 × 2~3 次模型调用/项目；超预算停止并记 `waiting_budget`，不降级为模板套话。
- 冷却：同 domain/email 90 天内不重复；已回复/成交的永久跳过。
- 知识库索引未就绪时暂停当日生成，并在“今日开发”顶部提示。

## 六、评分与排除

用你上传的《01-客户画像》作为评分标准：

- 硬性排除：竞品/包装供应商、无邮箱、国家或地区不符、黑名单域名、官网明显不相关。
- 评分维度：品类匹配、品牌调性（独立设计/手作/珠宝）、规模、内容活跃度、可联系性。
- LLM 输出结构化 JSON：`score` + 3 条理由 + 命中的画像信号；落库可解释，业务员能看到“为什么选它”。
- `minScore` 可配置；不足 15 个就少发，不用低分凑数。

## 七、业务员审核页（“今日开发”）

- 15 张卡片：客户/国家/评分/入选理由/官网摘要/草稿预览；
- 操作：批准并发送、修改后发送、跳过（进入冷却并记录原因）、整批标记；
- 发送时间窗与每日上限；发送后自动回到客户时间线；
- 未处理的草稿次日提醒，超过 3 天自动过期并释放配额。

## 八、质量与合规

- 只发 B2B 首封，带公司信息与退订方式；SMTP 日发送量控制在 15/项目 + 回复；
- 退信率/投诉超过阈值自动暂停当日发送并告警；
- 草稿必须通过现有依据审计（不编价格/MOQ/交期/认证）；
- 每条候选保留来源 URL 与抓取时间，便于追溯。

## 九、监控指标

- 运行：导入数、去重数、排除数、入选数、草稿数、失败明细；
- 业务：审核通过率、发送率、回复率、退信率、成交率；
- 每周用回复数据回灌评分（哪些画像特征回复高）。

## 十四、Hunter 补邮箱（2026-10-21）

第一次自动运行暴露“20 个官网只有 3 个有公开邮箱”后，接入 Hunter 作为补邮箱来源：

- 只在 Firecrawl 抓完仍没有邮箱时调用 `domain-search`；每次运行最多查 `hunterLimit`（默认 15，可配 0–50），避免额度失控。
- 取回的邮箱按“有名字的决策人优先、其次置信度”排序，取前 3 个；同时保存联系人姓名/职位、邮箱来源（`site` / `hunter`）和置信度。
- 评分：官网邮箱 +25，Hunter 邮箱 +20（理由里带置信度）；“可发送”仍然必须有邮箱。
- 转客户时优先用联系人姓名，备注里写清邮箱来源与来源 URL。
- 界面上候选会显示 `Hunter 98%` 标记和联系人姓名/职位。

回填今天已有的 12 个“待补联系方式”候选：

```
查询 12 个域名 → 11 个找到邮箱（其中 9 个带姓名/职位）
今日可发送：3 → 14；待补联系方式：12 → 1
```

注意：当前 Hunter 是 **Free 计划，50 credits**，日期重置 2026-10-23。按 15 个/天计算，两天就会用完；要长期跑需要升级付费计划（或把 `hunterLimit` 调到免费额度能承受的值）。

## 十五、审核通过自动生成草稿（2026-10-21）

- “转为客户”成功后，服务端立即：
  1. 建一个客户上下文的 Agent 会话（标题 `自动开发 · 客户名`）；
  2. 建首封开发信任务（goal 明确为“首封开发信”），`requestKey=prospect:<id>` 保证幂等；
  3. 把任务 id 存到候选的 `draftTaskId`，页面显示“查看草稿”。
- 任务执行复用现有 agent 任务 worker（`app.ts` 启动的 2 秒轮询），不需要额外调度；任务失败会显示在任务列表，不影响已建好的客户。
- 草稿完成后，“查看草稿”跳到客户详情并打开审核页（`?outreachTask=<taskId>`），业务员审核、修改、发送；发送仍由人操作。
- 实测：UncommonGoods 通过审核后约 18 秒生成草稿，收件人自动使用 Hunter 找到的联系人 `Dave Bolotsky`，主题 `A brief introduction`，状态 `awaiting_review`。
- 成本提示：每通过一个候选就产生一次完整的 AI 任务（约 1 分钟、消耗配额）；一次通过 14 个会排队执行，建议分批审核。

## 十六、LLM 画像评分（2026-10-21）

- 补全后的候选按 8 个一批交给模型，用《01-客户画像》打分：0–100 匹配分 + 最多 3 条理由；不匹配时返回 `exclude + 原因`。
- 综合分 = 规则分 × 40% + AI 分 × 60%；AI 可以判定“不是目标客户”直接排除，但**不能**把没有联系方式的候选变成“可发送”。
- AI 分数单独存到 `aiScore`，页面显示 `AI 88` 标记；AI 排除的候选仍留在“已跳过”分组，业务员可以人工翻案。
- 配置里新增“AI 画像评分”开关（默认开）；关闭后只用规则分，不产生额外模型调用。
- 成本：每 8 个候选一次调用。

对今天 14 个候选重新评分的结果：

```
AI 80+：brooklyncandlestudio 88、foundrae 80、lightmycandle 85（待补邮箱）
AI 排除：svsfinejewelry（多品牌零售商）、yankeecandle（大型企业，规模不符）
综合后：可发送 9、待补 1、低分 2、已跳过 7、已转客户 1
```

注意：AI 会按“规模/渠道”否掉一些真实品牌（比如 Yankee Candle），这是建议而不是判决；规则分和人工审核仍然保留最终决定权。

## 十八、结果归因与退信保护（2026-10-21）

- 已转客户的候选卡片现在显示 **已发 / 回复 / 退信** 三个数（按客户聚合开发信与来信），有回复时加“已回复”标记；数据来自 `DevelopmentLetter` 与 `MailMessage`，不影响其他客户。
- 退信保护：过去 24 小时“退信 ≥ 5 封”或“发出 ≥ 10 封且退信率 > 8%”时：
  - 调度器在启动当天生成前自动把该项目的 `enabled` 关掉，并写日志；

## 十一、风险

- **线索质量决定一切**：没有稳定的来源，15 个/天不可持续；低质线索只会消耗配额。
- **冷邮件送达率**：需要 SPF/DKIM、域名预热、低日发送量、及时处理退信。
- **自动建客户污染 CRM**：用候选池 + 人工审核，默认不直接进客户列表。
- **成本**：15 × 3 次调用/项目/天，需要预算上限与失败熔断。
- **合规**：即使 B2B 也要退订、真实发件人信息，遵守目标市场的反垃圾邮件规则。
