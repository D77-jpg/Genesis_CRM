# Genesis container runtime (H-13)

Build contexts are `server/` and `web/`, with multi-stage Dockerfiles at `server/Dockerfile` (Node 22, UID `node`) and `web/Dockerfile` (Nginx alpine, UID `nginx`). `compose.yaml` is **standalone**: `mongo` (private TCP 27017), `server` (private TCP 5000), and `web` (TCP 8080, bound only to host loopback, default `127.0.0.1:8080`). Only an operator-managed HTTPS reverse proxy should accept public 80/443 and forward the dedicated CRM hostname to this loopback socket. The API and Mongo are **never host-published**. Do not expose standalone HTTP ingress to the public Internet. The eventual AutoForceAI deployment must provide its own TLS/ACME ingress and dedicated `crm.example.com` hostname; this repo does not claim HTTPS production acceptance.

## Initial installation

1. Install Docker Engine with Compose v2, provide DNS and a trusted ACME-issued certificate on your **external** TLS proxy. Forward `https://crm.example.com` to `http://127.0.0.1:8080` and **replace** rather than append `X-Forwarded-For`; send the canonical `Host`. Restrict proxy access to trusted operators until real HTTPS is working. Prefer a private Docker network shared with ingress rather than publishing the loopback socket if ingress itself runs in Docker. Do not mount the Docker socket into containers.
2. Copy `production.env.example` to `.env.production` (Git ignored; chmod 600 on Linux). Replace every placeholder with separately generated values. Never put real credentials into source, Docker build args, Docker image layers, or `VITE_*` variables. Compose interpolates `.env.production`; `MONGODB_URI` must contain URI-escaped Mongo credentials (encode reserved characters including `$` as `%24`; Compose interpolates `$` in values). Database name is `cdlm`, authentication database `admin`; for mature deployments provision a least-privilege app user instead of the bootstrap root account. Keep `MONGO_ROOT_PASSWORD`, `JWT_SECRET`, `ADMIN_PASSWORD`, and `MAIL_CREDENTIAL_ENCRYPTION_KEY` stable across upgrades; changing encryption key prevents old mailbox credentials decrypting.
3. `docker compose --env-file .env.production config --quiet` to validate syntax. **Warning:** verbose `config` outputs secrets; never paste it into CI logs. `docker compose --env-file .env.production build` then `docker compose --env-file .env.production up -d --wait`; verify `curl -fsS http://127.0.0.1:8080/api/health` shows `data.status=ok`, then test through the public HTTPS hostname. On fresh Mongo volumes the Mongo initialization may take a while. Bootstrap admin is created by the server only at first start; do not run demo seed on business databases.
4. Log in at the HTTPS CRM hostname, test a non-sensitive attachment and a mock mail send. Set `TRACKING_BASE_URL` to the exact public HTTPS CRM origin for email tracking. This is a rehearsal until TLS, login, restore and integration E2E have all passed.

The frontend's `VITE_API_BASE_URL` is a **build-time** variable (default `/api`, not a runtime environment variable). With the default, browser requests stay on the CRM hostname; `web/nginx.conf` preserves `/api/...` and forwards to `server:5000`, avoiding CORS. Build a different web image for a different API address (`VITE_API_BASE_URL=https://crm.example.com/api`) and set server `CORS_ORIGIN` to the exact frontend origin if cross-origin. `VITE_APP_TITLE` is also build time. The `VITE_API_PROXY_TARGET` in `web/.env.example` applies **only to Vite dev/preview**, never the Nginx container. No HMR or WebSocket forwarding in production. Nginx caps upload request bodies at 26 MiB (Express caps JSON at 25 MiB), applies security headers and proxy timeouts; external ingress must enforce equal or tighter limits and configure trusted HTTPS headers/security policy. The app trusts one proxy hop; prevent untrusted clients from directly accessing the internal API.

`MAIL_TRANSPORT=mock` and `IMAP_ENABLED=false` are safe initial defaults. To enable SMTP/IMAP or AI provide validated credentials through a protected runtime secret-injection mechanism and explicitly add the appropriate Compose environment mapping; the sample deliberately omits all such secrets. The server refuses weak/missing production JWT/admin/mail encryption keys at startup. Mongo root authentication is enabled; do not use public-facing database ports.

## Operations

- **Upgrade:** back up Mongo, uploads and key material separately before changes; pin reviewed image digests/tags in deployment, `git pull` reviewed branch/main, rebuild both images and `docker compose --env-file .env.production up -d --wait`. Existing volumes persist. Startup migrations run in the API; review any migration before rolling forward.
- **Rollback:** keep a tested image of the previous commit and restore its matching database/uploads snapshot **only in a controlled maintenance window** when schema changes are incompatible. Never run `down -v` on business data. Verify JWT/encryption keys remain the same.
- **Backups:** named volumes are `mongo_data`, `uploads` (`/data/uploads`), `backups` (`/backups`). H-12 `scripts/mongo-backup.cjs` is host-side and requires MongoDB Database Tools and a **protected backup destination**. The volume alone does not schedule backup and is not a backup of uploads. To use the container backup volume, a separate restricted backup job/tooling image must mount it and run the H-12 command with its own restricted Mongo URI; the API image has no database tools. Refer to [H-12 backup & isolated restore rehearsal](mongo-backup.md), including independent uploads snapshot and external encryption key. Do not run restore against live Mongo.
- **Troubleshooting:** `docker compose --env-file .env.production ps`, `docker compose --env-file .env.production logs --tail=100 server web mongo` (logs could contain PII; restrict access), then probe `/api/health`. Mongo failures surface as HTTP 503 or server startup failure; inspect Mongo health and volume disk free space. 502 at ingress: check TLS upstream and `web`/`server` health. Browser API 404: rebuild web with `/api` and verify reverse proxy does not strip `/api`. Refused startup: replace placeholder credentials and inspect env validation without printing secret values. Unexpected upload 413: align ingress limit with Nginx and Express 25 MiB JSON cap. Rotate logs and monitor resource budgets (`mongo` 1 GiB/1 CPU, `server` 1 GiB/1 CPU, `web` 256 MiB/0.5 CPU) to suit workload.

Test packaging without production credentials: `node --test scripts/docker-runtime.test.cjs scripts/mongo-backup.test.cjs`, `docker compose --env-file production.env.example config --quiet`, and `docker compose --env-file production.env.example build` (build only; placeholder env MUST NOT be used for production startup). For a real smoke use an isolated test env with generated random strong secrets and no business database; remove test volumes explicitly only after verifying project name/volume ownership.
